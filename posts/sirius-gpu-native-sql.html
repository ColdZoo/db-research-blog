Sirius: GPU 时代的分析处理重构

Sirius: GPU 时代的分析处理重构

Sirius: Rethinking Analytics Processing in the GPU Era

    • 摘要

    随着 GPU 在数据分析领域的普及，传统的以 CPU 为中心的 SQL 引擎架构遇到了瓶颈。我们提出了 Sirius，一个开源的 GPU 原生 SQL 查询引擎，专为 GPU 时代设计。

    Sirius 使用 libcudf 作为主要计算引擎，基于 Substrait 与现有数据库系统无缝集成。它为各种数据系统提供了即插即用的 GPU 加速。在生产工作负载（TPC-H、ClickBench）上的评估显示，Sirius 相比 DuckDB 实现了 8.3 倍的成本效率提升，相比 Apache Doris 实现了 12.5 倍的查询速度提升。

    核心贡献

    1. GPU 原生架构

    传统 GPU 数据库的问题：

  • CPU 主导的查询规划
  • GPU 仅作为加速器
  • CPU-GPU 数据传输频繁
  • 无法充分利用 GPU 并行性

    • Sirius 的设计：

  • GPU 作为主计算引擎
  • 查询规划和执行全部在 GPU 上
  • 最小化 CPU-GPU 交互
  • 充分利用 GPU 并行性

    • 2. 基于 libcudf 的计算引擎

    libcudf 是 NVIDIA 开发的 GPU 加速数据操作库：

    功能说明
    列式操作面向列的 GPU 原语
    字符串处理GPU 加速字符串操作
    时间函数高效日期/时间计算
    聚合并行 SUM/COUNT/AVG 等
    连接GPU 原生 Join 实现

    3. Substrait 集成

    Substrait 是一个跨平台查询执行计划规范：

    
任何支持 Substrait 的数据库
   ↓
  生成 Substrait 计划
   ↓
  Sirius (GPU 执行)
   ↓
  返回结果

    优势：

  • ✅ **即插即用** — 无需修改现有数据库
  • ✅ **标准化** — 遵循开放标准
  • ✅ **可扩展** — 支持多种数据系统

    • 4. 开源与可扩展

    Sirius 是开源项目，提供：

  • 完整的源代码
  • 详细的 API 文档
  • 社区支持
  • 易于集成到现有系统

    • 架构设计

               ↓

         GPU (NVIDIA CUDA)

    查询执行流程

    1. SQL 解析 — 客户端系统解析 SQL

    2. Substrait 生成 — 生成跨平台执行计划

    3. 计划传递 — Substrait 计划传给 Sirius

    4. GPU 优化 — Sirius 转换为 GPU 优化计划

    5. libcudf 执行 — GPU 内核并行执行

    6. 结果返回 — 结果传回客户端

    为什么重要

    1. 定义 GPU 原生 SQL 引擎标准

    传统 GPU 数据库：

  • 在 CPU 引擎上添加 GPU 加速器
  • CPU 仍然是主计算单元

    • Sirius：

  • GPU 作为主计算引擎
  • CPU 仅负责轻量级调度

    • 2. Substrait 的实际应用

    Substrait 一直是一个理论标准，Sirius 展示了它的实际价值：

  • **跨系统集成** — DuckDB + Sirius = GPU 加速
  • **开放生态** — 任何系统都可以使用 Sirius
  • **标准化** — 避免厂商锁定

    • 3. 成本效益显著

    企业关心的问题：

  • ❌ GPU 是否昂贵？
  • ✅ 是，但成本效率是 CPU 的 8 倍

    • 结论：虽然 GPU 单价高，但查询速度快 8-12 倍，总体成本大幅降低。

    技术挑战与解决方案

    挑战 1: 查询优化

    问题：GPU 优化的查询策略与 CPU 不同

    解决方案：

  • GPU 感知的代价模型
  • 并行度自适应调整
  • 内存访问模式优化

    • 挑战 2: 内存管理

    问题：GPU 内存有限，需要高效分配

    解决方案：

  • 基于列的内存分配
  • 池化管理减少碎片
  • 异步数据预取

    • 挑战 3: 复杂查询支持

    问题：嵌套查询、子查询、窗口函数的 GPU 实现

    解决方案：

  • 递归查询计划转换
  • 窗口函数的 GPU 原语
  • 子查询展开优化

    关键洞察

    1. GPU 原生 > CPU+GPU 混合

    传统 GPU 数据库尝试在 CPU 架构上添加 GPU：

    
CPU 查询规划 → GPU 加速器 → CPU 聚集

    Sirius 完全重新设计：

    
GPU 查询规划 → GPU 执行 → GPU 聚集

    2. Substrait 的战略价值

    Substrait 是一个"桥梁"：

  • **数据系统** → 生成 Substrait 计划
  • **执行引擎** → 执行 Substrait 计划

    • 这使得 Sirius 可以：

  • 无需修改 DuckDB/Trino
  • 即插即用的 GPU 加速
  • 生态系统快速扩展

    • 3. 成本效率是关键指标

    企业关心的不是"最快"，而是"最高性价比"：

    指标说明
    绝对速度学术关注点
    成本效率企业关注点

    Sirius 在两者上都表现优秀，这对商业成功至关重要。

    未来方向

    1. 多 GPU 扩展

  • 分布式查询执行
  • GPU 间通信优化
  • 跨 GPU 聚集

    • 2. 更多 Substrait 算子

  • 窗口函数优化
  • 递归查询支持
  • 复杂连接算法

    • 3. 自适应执行

  • 运行时统计信息收集
  • 动态查询计划调整
  • 自适应并行度

    • 4. 硬件多样性支持

  • AMD ROCm 支持
  • Apple Silicon (Metal) 支持
  • 云原生优化

    • 结论

    Sirius 重新定义了 GPU 数据库的架构：

    1. GPU 原生 — GPU 是主计算引擎，不是加速器

    2. Substrait 集成 — 即插即用的跨系统集成

    3. 成本效率领先 — 比 CPU 系统高 8-12 倍

    4. 开源可扩展 — 社区驱动的持续创新

    这项工作证明了：GPU 原生架构是数据分析的未来方向，而非在 CPU 引擎上添加 GPU 加速。
