在 GPU 上高效处理连接和分组聚合

Efficiently Processing Joins and Group-By Aggregations on GPUs

论文信息

  • **会议**: SIGMOD 2025
  • **作者**: Bowen Wu, Dimitris Koutsoukos, Gustavo Alonso
  • **机构**: ETH Zürich（苏黎世联邦理工学院）
  • **论文编号**: SIGMOD 2025
  • **arXiv**: 2312.00720
  • **原文链接**: https://arxiv.org/abs/2312.00720
  • **PDF**: https://arxiv.org/pdf/2312.00720

    • 摘要

    随着 GPU 在数据库领域的广泛应用，基于 GPU 的连接（Join）和分组聚合（Group-By Aggregation）实现需要重新审视。传统的研究主要关注单个操作符的优化，但忽略了查询执行的整体优化空间。

    我们系统性地分析了 GPU 上连接和聚合的性能特征，识别了四个主要改进领域：

    1. GPU 查询优化 — 查询计划需要考虑 GPU 的并行性和内存特性

    2. 连接算法选择 — 不同的连接策略在 GPU 上的性能差异巨大

    3. 聚合优化 — Group-By 操作需要针对 GPU Warp 执行模型优化

    4. 内存管理 — GPU 内存的高效分配和重用

    我们在代表性工作负载（TPC-H、TPC-DS）上进行了全面评估，验证了这些优化带来的显著性能提升。

    核心贡献

    1. GPU 查询优化

    传统查询优化器的局限性：

  • 基于 CPU 的代价模型
  • 不考虑 GPU 的并行特性
  • 忽略 Warp 执行模式的影响

    • GPU 感知的优化：

    传统代价模型GPU 感知代价模型
    I/O 代价I/O + PCIe 传输代价
    CPU 计算代价GPU Warp 并行代价
    缓存未命中GPU 共享内存/寄存器压力
    基数估计基数 + 并行度调整

    关键洞察：

  • **选择性估算** — GPU 上高选择性查询的代价可能低于低选择性（因为并行过滤更有效）
  • **连接顺序** — 小表作为 Build 端，大表作为 Probe 端（与 CPU 一致）
  • **内存预算** — 考虑 GPU 内存限制，选择合适的算法

    • 2. 连接算法优化

    论文比较了多种连接算法在 GPU 上的性能：

    连接算法说明GPU 优化要点
    Hash Join最常用合并访问、共享内存优化
    Sort-Merge Join有序数据归并排序算法、块级处理
    Nested Loop Join小数据集共享内存缓存小表
    Radix Join整数键位分区、Warp 级并行

    关键发现：

    1. Hash Join 在 GPU 上最优

    - 大规模数据集下表现稳定

    - GPU 上的 Hash 碰撞处理高效

    2. Sort-Merge Join 适用于有序输入

    - 避免 Hash 构建开销

    - 适合流水线查询

    3. Nested Loop Join 仅适用于极小数据集

    - 表大小 < 1 MB 时有优势

    - 更大数据集下性能急剧下降

    3. 分组聚合优化

    Group-By Aggregation 是分析查询的核心操作，GPU 实现面临挑战：

    挑战：

    挑战说明解决方案
    线程冲突多线程写入同一分组原子操作 / 原子加
    负载不均衡某些分组包含大量数据动态负载均衡
    内存碎片中间结果分散存储预分配 + 重用
    合并阶段局部聚合需要合并高效的两阶段聚合

    优化策略：

    1. 基于 Warp 的聚合

    ```

    每个 Warp 处理一组数据

    Warp 内的线程协作处理一个分组

    使用 Warp 内的共享内存

    优势：减少全局内存访问

    ```

    2. 两阶段聚合

    ```

    阶段 1: 线程块内局部聚合 (共享内存）

    阶段 2: 全局合并 (全局内存）

    优势：减少原子操作次数

    ```

    3. 预分配哈希表

    - 根据基数估计预分配

    - 避免运行时动态分配

    - 重用哈希表减少分配开销

    4. 内存管理与零拷贝

    传统 GPU 编程模式：

    
CPU 内存 → 拷贝到 GPU 内存 → GPU 处理 → 拷贝回 CPU 内存

    零拷贝优化：

    
CPU 内存 → GPU 直接访问 (CUDA Unified Memory 或 P2P)
         → GPU 处理
         → 结果留在 GPU 内存（供后续查询）

    优势：

  • 减少 PCIe 传输开销
  • 支持查询流水线
  • 提升整体吞吐量

    GPU 内核优化

    连接内核：

    
// 示例：优化的 GPU Hash Join
__global__ void hash_join_kernel(
    Key* build_keys, Value* build_values, int build_size,
    Key* probe_keys, Value* output, int probe_size
) {
    // 线程块协作构建哈希表
    __shared__ HashTable local_hash;

    // 阶段 1: 构建
    build_local_hash(&local_hash, build_keys, build_values);

    __syncthreads();  // 同步

    // 阶段 2: 探测
    probe_local_hash(&local_hash, probe_keys, output, probe_size);
}

    聚合内核：

    
// 示例：基于 Warp 的聚合
__global__ void group_by_kernel(
    Key* input_keys, Value* input_values, int size,
    Key* output_keys, Value* output_values
) {
    // Warp 内协作
    int warp_id = (blockIdx.x * blockDim.x + threadIdx.x) / 32;
    int lane_id = threadIdx.x % 32;

    // Warp 级聚合
    warp_reduce_aggregate(
        input_keys, input_values, size,
        output_keys + warp_id,
        output_values + warp_id
    );
}

    为什么重要

    1. 系统性优化 vs 局部优化

    传统研究关注：

  • ❌ 单一连接算法优化
  • ❌ 单一聚合算子优化
  • ❌ 局部性能提升

    • 本文采用系统性方法：

  • ✅ 查询端到端优化
  • ✅ 考虑所有阶段的协同效应
  • ✅ 整体性能提升 4x

    • 2. GPU 感知的查询优化

    传统代价模型不适用于 GPU：

  • CPU 串行执行代价 ≠ GPU 并行执行代价
  • CPU 缓存行为 ≠ GPU 共享内存行为
  • Warp 执行模型需要特殊考虑

    • 论文证明了 GPU 感知的优化器能带来 1.5x 提升。

    • 技术挑战与解决方案

    挑战 1: 连接算法选择

    问题：不同连接算法在 GPU 上的性能差异巨大，自动选择困难。

    解决方案：

  • 基于数据特征（大小、基数、有序性）的启发式规则
  • 运行时评估小样本
  • 动态选择最优算法

    • 挑战 2: 聚合负载均衡

    问题：真实数据偏斜严重，某些分组包含大量数据。

    解决方案：

  • 动态负载均衡算法
  • 重度偏斜分组特殊处理
  • 负载感知的线程分配

    • 挑战 3: GPU 内存碎片

    问题：多次查询导致 GPU 内存碎片化，降低性能。

    解决方案：

  • 内存池化管理
  • 预分配固定大小块
  • 查询间内存重用

    查询优化最重要，连接算法差异不大

    • 结论

    本论文系统性地分析了 GPU 上连接和聚合的性能特征，识别了四个关键优化领域：

    1. GPU 查询优化 — 基于并行性和内存特性的代价模型

    2. 连接算法选择 — Hash Join 在 GPU 上最优

    3. 聚合优化 — Warp 级两阶段聚合，减少原子操作

    4. 内存管理 — 零拷贝访问，内存池化管理

    在 TPC-H 和 TPC-DS 上的评估显示，这些优化带来 4.0x 的整体性能提升。

    这项工作证明：系统性、端到端的优化远优于局部优化，为未来的 GPU 查询引擎提供了重要基础。
